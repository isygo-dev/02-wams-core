# isygoPlan

isygoPlan accepts a generic planning problem, validates and normalizes it, then creates a tracked solve job. The
runnable API host is `10-starter-test/80-plan-management/04-plan-service`. The module is split like the Edyra Pilot:

| Module                  | Content                                                                                                   |
|-------------------------|-----------------------------------------------------------------------------------------------------------|
| `01-plan-jpa`           | `eu.isygoit.model` (`PlanJob` PostgreSQL entity, `PlanLog` Cassandra row, `AppNextCode`, `ApiPermission`) and `eu.isygoit.repository` |
| `02-plan-shared`        | `eu.isygoit.api.PlanJobServiceApi`, `eu.isygoit.dto.{request,response,data}`, `eu.isygoit.enums`, `JobNotFoundException`, `ImmutableJsonMap` |
| `03-plan-starter-parent`| controller, services, mappers, exceptions, solver engines, Kafka producers, Camel processors, configuration |
| `04-plan-starter-ui`    | Vaadin UI library (views, `PlanFeignService`, i18n bundles); not runnable on its own                       |

Package map of the starter parent: `eu.isygoit.controller` (`PlanJobController`), `eu.isygoit.service` (interfaces),
`eu.isygoit.service.impl` (job lifecycle: `PlanJobService`, `PlanLogService`, `JobProcessor`, `JobDispatchService`,
`JobDispatchRecovery`, `JobStopMonitor`, `JobWorkerShutdown`, `TenantScope`, `NextCodeService`),
`eu.isygoit.service.impl.planning` (`PlanningService`, request/solution validators, normalizer, solve concurrency guard),
`eu.isygoit.mapper`, `eu.isygoit.dto.tech` (`PlanJobMessage`, `ApiPermissionDto`), `eu.isygoit.exception` and
`eu.isygoit.exception.handler` (`PlanExceptionHandler`), `eu.isygoit.config`, `eu.isygoit.solver` (engine contracts and
registries) with `eu.isygoit.solver.cpsat`, `eu.isygoit.solver.timefold` and `eu.isygoit.solver.handler`,
`eu.isygoit.async.kafka` (producers) and `eu.isygoit.async.camel.processor` (consumer and dead-letter processors).
Services call the Spring Data repositories directly: there are no ports or adapters.

## Identity model

A `PlanJob` has three identifiers:

- `id`: `Long` surrogate key (database sequence); the only identifier used in REST paths, Kafka messages and the UI.
- `code`: business code generated by the next-code service, format `PLN-000001`, unique per tenant.
- `clientRef`: optional client-chosen idempotency key (`meta.clientRef`, at most 128 characters), unique per tenant.
  Submitting the same `clientRef` again returns the existing job instead of creating a second one.

Every read and write is scoped to the tenant of the caller; a job of another tenant answers `404`.

## Flow

1. `POST /api/v1/private/plan/job/submit` validates the request against the configured limits, resolves the solver,
   allocates the code and persists a `CREATED` job row with the request JSON, then returns `202 Accepted` with the
   `PlanJobDto` (`id`, `code`, `status`, ...). With `app.plan.execution.kafka-enabled=true` the job is dispatched
   to Kafka (see Messaging) and the Kafka consumer processes it sequentially. With the property set to `false`, a
   bounded in-process executor runs the same job processor without using Kafka for job dispatch.
2. Clients poll `GET /{id}` until a terminal status (`SUCCEEDED`, `INFEASIBLE`, `FAILED`, `CANCELLED`), then fetch the
   persisted result with `GET /{id}/result`. The worker claims the job (`CREATED` to processing) so a duplicate delivery
   never solves it twice, loads the persisted request by id, solves, and stores the terminal state and result. In Kafka
   mode the offset is committed only after that. A recovery sweep redispatches `CREATED` jobs whose last dispatch is
   older than `redispatch-grace-seconds` (at most `max-dispatch-attempts`, then `DISPATCH_FAILED`) and marks jobs
   still in `NORMALIZING` or `SOLVING` as failed when the solver time limit plus
   `app.plan.execution.stale-job-grace-seconds` (default 240 seconds) has elapsed. On shutdown the worker waits up to
   `shutdown-wait-seconds` for the running solve.
3. Job logs are published best-effort and asynchronously to the plan-logs topic; a separate sequential Camel route
   writes them to Cassandra and commits only after the write succeeds.
4. PostgreSQL is the single source of truth for status and result. There is no status cache: every read goes to the
   database.

### Messaging

| Topic (`spring.kafka.topics.*`)  | Key              | Body                                        | Producer / consumer                                  |
|----------------------------------|------------------|---------------------------------------------|------------------------------------------------------|
| `isygo.plan.jobs` (`plan-jobs`)  | job id (UTF-8)   | `{"jobId":123,"tenant":"acme"}`             | `PlanJobKafkaProducer` / `PlanJobKafkaConsumerProcessor` |
| `isygo.plan.logs` (`plan-logs`)  | job id           | JSON `LogEntry`                             | `PlanLogKafkaProducer` / `PlanLogKafkaConsumerProcessor` |
| `isygo.plan.jobs.dlq`            | original key     | original payload + failure headers          | `PlanJobDeadLetterProcessor`                         |
| `isygo.plan.logs.dlq`            | original key     | original payload + failure headers          | `PlanLogDeadLetterProcessor`                         |

The job message is only a pointer: the planning request is never put on the wire, the worker loads the persisted
request by `jobId`. The key is the job id so a job always lands on the same partition and the id can be recovered from
the key when the body is unreadable. Failures are redelivered with bounded exponential backoff
(`app.plan.kafka.retry.*`) and then dead-lettered; poison messages go to the DLQ immediately. The Camel routes
(`camel/plan-job-camel-routes.xml`, `camel/plan-log-camel-routes.xml`, `camel/email-camel-routes.xml` in the host) are
consumer routes only: producers are plain Spring beans extending the stack producer types, there are no publisher routes.
The `plan-jobs` topic has one partition: jobs are processed strictly sequentially.

### Schema

PostgreSQL schema `plan` (tables `plan_job`, `app_next_code`, ...) is created and updated by Hibernate
(`ddl-auto: update`; the schema itself by the Hikari `connection-init-sql`). Spring Data creates the Cassandra keyspace
and the `plan_log_entries` table (`create-if-not-exists`). There are no SQL, CQL or Flyway scripts. `plan_job` has
unique constraints on `(tenant, code)` and `(tenant, client_ref)`. The Cassandra log partition key is
`(tenant, job_id, bucket_start)`; `event_time` and `event_id` are descending clustering columns. Six-hour buckets bound
partition growth and tenant is required when reading logs. Log retention is 30 days, applied on every write as a
Cassandra TTL (`InsertOptions`); log-range reads clamp to the retained window. A migration tool (Flyway) will be
introduced before the first production deployment.

## Supported planning semantics

- Tasks are required by default; required tasks receive exactly one resource/slot assignment. Set `required: false` for
  an optional task, which may be listed in `solution.unassignedTasks`. `maximize_task_priority` rewards assigning
  higher-priority optional tasks when capacity is limited. A resource is available in a slot up to its configured
  capacity; the default is one. Resource `attributes.capacity` and `resource_capacity` constraints may set a higher or
  lower limit. `task.candidates.capabilityTags` must all exist in `resource.attributes.capabilities`.
- `task_eligibility` constraints require a `scope` of `{ "kind": "task", "value": "<taskId>" }` and accept optional
  `params.resourceIds` and `params.slotIds` lists.
- `minimize_resource_cost` reads numeric `resource.attributes.cost`; `minimize_slot_cost` reads numeric
  `slot.attributes.cost`; `maximize_task_priority` reads numeric `task.attributes.priority`. Objective weights scale the
  contributions.
- `SOFT` is supported for `task_eligibility`; `resource_capacity` must use hard enforcement. Authorized relaxable
  constraints are considered in ascending `relaxation.priority`, and `solverOptions.relaxationLevels`, when supplied, is
  an allow-list of constraint IDs. `maxRelaxation` is binary: `0` keeps a constraint active and `1` permits dropping the
  whole constraint; fractional values are rejected. `STRICTLY_REQUIRED` constraints are never relaxed.
- Available engines are `cp_sat` and `timefold`. Solver time is bounded by `solverOptions.maxTimeSeconds`.
- On Windows, CP-SAT loads native OR-Tools binaries; use a JDK with a current Microsoft C++ runtime. A stale
  `msvcp140.dll` bundled with a JDK can crash the solver process; use an updated JDK distribution or run on Linux.
- `solverOptions` may be omitted or partially specified. Missing values default to `engine=cp_sat`,
  `maxTimeSeconds=30`, `numWorkers=8`, `seed=0`, `logSearch=false`, and an empty `relaxationLevels` list. Explicit
  `maxTimeSeconds` values must be positive; `numWorkers` is clamped to `app.plan.limits.max-workers`.
- Task, resource, slot, constraint-parameter, and diagnostic-detail maps preserve JSON `null` values.
- Timefold uses 32-bit hard/soft scores; requests whose worst-case combined soft score exceeds `Integer.MAX_VALUE` are
  rejected instead of failing during solving.
- Requests are bounded by `app.plan.limits.*` (tasks, resources, slots, variables, constraints, request bytes, solver
  time, workers); a solve waits at most `solve-queue-timeout-seconds` for a free solver slot.

The smoke test in `examples/` (`smoke-test.ps1` / `smoke-test.sh`, with golden scenario requests G1 to G3) submits each
scenario with a fresh `meta.clientRef` and polls for completion. A JSON Schema resource is not currently present in the
repository.

Runtime versions: Java 17 and Spring Boot 3.5.16 (inherited through `service-stack-parent`, which uses
`spring-boot-starter-parent` 3.5.16). The `3.0.7` value in the `service-core` POM is the legacy property of that
parent, not the effective runtime version.

## Local configuration

The service port is `40417`. Build the runnable jar first (from `02-wams-core`; nothing is built inside Docker), then
start the dependencies and the service with Docker Compose from this folder:

```powershell
cd 02-wams-core
mvn -pl 10-starter-test/80-plan-management/04-plan-service -am package -DskipTests
cd 08-plan-core
$env:PLAN_JDBC_PASSWORD = "change-me"
docker compose up --build
```

Compose builds `09-docker/core-plan.Dockerfile` with `02-wams-core` as build context (it copies, like
`core-mms.Dockerfile`, the host jar `10-starter-test/80-plan-management/04-plan-service/target/plan-management-service-*.jar`
plus `target/uploads` and `target/camel` produced by the host POM; glibc `eclipse-temurin:17-jre`
base because the OR-Tools natives do not run on Alpine). It starts PostgreSQL (empty database `isygo_plan`; the schema
`plan` and its tables are created by the application), a single-node KRaft Kafka with a one-shot `kafka-init`
that creates `isygo.plan.jobs`, `isygo.plan.jobs.dlq`, `isygo.plan.logs` and `isygo.plan.logs.dlq`, and Cassandra
(keyspace `isygoit` and tables created by the application). Data lives in named volumes (`docker compose down -v`
resets it). The plan container waits for all dependencies to be healthy and exposes its own `/actuator/health`
healthcheck.

Configuration: there is no `local` profile file. The service reads `plan-service.yml`, which the Config server serves
from `10-edyra/09-docker/config-files/plan-service.yml` (the host `application.yml` imports
`optional:configserver:...`). Compose does not run the config service: it mounts that file at
`/config/plan-service.yml`, sets `SPRING_CONFIG_IMPORT=optional:file:/config/plan-service.yml`, disables the config
client and overrides the connection settings (datasource, Kafka, Cassandra) through environment variables. To
use a running config-service instead, drop the mount/import and point `spring.config.import` at it. Defaults in the
file: the pilot infrastructure keys (`spring.hazelcast.config`, `spring.cache.jcache.provider`, Kafka topics
`register-api-permission` / `register-account` / `send-email`, `app.email.*`, `app.upload.directory`, `app.i18n.*`,
`app.jwt.*`, `app.password.*`, `app.create.ifNotExists.*`, `app.feign.*`, `jasypt.*`; no `spring.mail` block, the pilot
sends mail through Kafka to MMS), `ddl-auto: update` with `connection-init-sql: CREATE SCHEMA IF NOT EXISTS plan`, Cassandra
`schema-action: create-if-not-exists` with `create-keyspace: true`, the plan topics (`spring.kafka.topics.plan-jobs`,
`plan-logs`, `plan-jobs-dlq`, `plan-logs-dlq`), `app.plan.kafka.*` (poll intervals, send timeout, retry/backoff),
`app.plan.execution.*` (`kafka-enabled` from `PLAN_KAFKA_ENABLED`, default `true`; `false` dispatches jobs to the
in-process executor, the plan-log routes still use Kafka; recovery, redispatch, stop-poll and shutdown settings),
`app.plan.limits.*` and `app.security.cors-allowed-origins`. The host `application-prod.yml` (profile `prod`) only
overrides the actuator exposure; datasource, Kafka and Cassandra settings come from the central file or from the
environment variables `PLAN_JDBC_URL`, `PLAN_JDBC_USERNAME`, `PLAN_JDBC_PASSWORD`, `KAFKA_BOOTSTRAP_SERVERS`,
`PLAN_CASSANDRA_CONTACT_POINTS`, `PLAN_CASSANDRA_PORT`, `PLAN_CASSANDRA_LOCAL_DATACENTER` and `PLAN_CASSANDRA_KEYSPACE`.

Set `SPRING_PROFILES_ACTIVE=prod` in production. Do not rely on the compose `SimpleStrategy` keyspace initialization in production.

The API lives under `/api/v1/private` and is protected by the stack JWT filter; the smoke test accepts an optional
bearer token (`-Token` / `TOKEN`).

## API

`eu.isygoit.api.PlanJobServiceApi` (`IMappedCrudApi<Long, PlanJobMinDto, PlanJobDto>`) is implemented by
`PlanJobController` at `/api/v1/private/plan/job`. `PlanJobMinDto` carries `id`, `code`, `tenant`, `clientRef`,
`engine`, `status`, timestamps, `errorCode` and `message`; `PlanJobDto` adds `request`, `result` and `diagnostics`.
Errors leave the service as the same `ApiError` body, produced by `PlanExceptionHandler`.

| Method and path (under `/api/v1/private/plan/job`) | Purpose |
|----------------------------------------------------|---------|
| `POST /submit`                                     | Submit a `PlanningRequest`; `202 Accepted` with the `PlanJobDto` (status `CREATED`); the same `meta.clientRef` returns the existing job |
| `GET /{id}`                                        | Inherited: fetch one job (`PlanJobDto`) |
| `GET` (paged), `GET /list`, `GET /filter`        | Inherited: paged and filtered job lists of the tenant (`PlanJobMinDto`) |
| `DELETE /{id}`                                     | Inherited: delete a job in a terminal state only (`409` otherwise); its Cassandra logs expire under the 30-day TTL |
| `GET /{id}/request`                                | The stored planning request |
| `PUT /{id}/request`                                | Replace the request while the job is `CREATED` (`409` afterwards) |
| `GET /{id}/result`                                 | The `SolveResult` once the job has completed |
| `GET /{id}/result/export?format=json\|csv`         | Download the result as JSON or CSV |
| `GET /{id}/logs?from&to&minLevel&limit`            | Recent logs or an ISO-8601 `from`/`to` range; optional `minLevel` and `limit` (default 100, max 1000) |
| `POST /{id}/stop`                                  | Request cancellation of a `NORMALIZING` or `SOLVING` job (moves through `STOPPING` to `CANCELLED`) |
| `POST /{id}/cancel`                                | Cancel a queued (`CREATED`) job before processing starts (`409` if already processing or terminal) |
| `POST /validate`                                   | Validate and normalize a request without creating a job (`ValidationReportDto`) |
| `GET /capabilities`                                | Available solvers, constraint types and objective types (`CapabilitiesDto`) |
| `GET /dashboard?limit=50`                          | Status counts and recent jobs for the management dashboard (`JobDashboardSummary`, limit max 500) |

Creating or updating a job through the generic CRUD endpoints (`POST`, `PUT /{id}`) is rejected with `405`: jobs are
created by `/submit` and their request is changed by `PUT /{id}/request`.

- `GET /actuator/health`: health/liveness endpoint.

## Management UI

The Vaadin UI is implemented in the separate library module `04-plan-starter-ui`, following the Edyra Pilot starter UI
layout (`04-pilot-starter-ui`) and shared dashboard components. Its views call the plan API through `PlanFeignService`,
a Feign client that extends `PlanJobServiceApi`; jobs are identified by their `Long` id and their code. Its central
config is `plan-ui.yml` (port `60607`, derived from `edyra-pilot-ui.yml`; it has no datasource and no camel routes, it
only calls `plan-service` through Feign). The runnable host `10-starter-test/80-plan-management/04-plan-service`
currently depends only on `plan-management-starter-parent` (API, solver, Kafka/Camel, persistence): it does **not**
include the UI starter, serves no `/plan` pages and has no plan navigation provider of its own. The UI is meant to be
added to a UI host (for example the combined `wams-starter-ui`). Once hosted there, `/plan` shows the dashboard, status
summary, recent jobs, and job lookup by id; `/plan/jobs` provides grid/card views, job submission, created-job
editing/cancellation, active-solver stopping, and terminal-job deletion; `/plan/logs` shows a selected job's logs with a
details action.
